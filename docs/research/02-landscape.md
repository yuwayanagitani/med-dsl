# R2：既存体系・研究・実装の一次比較

調査日：2026-10-18。状態：R2 の資料比較と検証候補の選定を完了。実装の採用、実データでの性能検証、利用条件の確定は未完了。

## 1. 結論

**共通モデル、概念合成、論理的な意味差分には先行例があります。** MedDSL は、これらを再利用しながら、臨床文脈・情報源・比較不能を含むコード移行の監査を組み立てられるかを検証します。独自体系の必要性と優位性は引き続き仮説です。

今回の選定は次のとおりです。D02 の検証候補を選定し、採用判断は R5 に残します。

| 項目 | 選定 | 理由 |
| --- | --- | --- |
| 比較基準 | 人が作成した、方向・用途・版・意味関係・条件を持つ FHIR ConceptMap による直接対応 | 単純な辞書より強い既存方式と比べ、独自部分の効果を過大評価しないため |
| 次に検証する基盤 1 | HAPI FHIR | 対応表の管理・変換操作・版指定を調べるため |
| 次に検証する基盤 2 | ROBOT と、その対応推論器 | OWL の含意・整合性・導出根拠を使える範囲を調べるため |
| 情報モデルの参照 | openEHR、FHIR の臨床リソース | 概念、記録文脈、臨床テンプレートを分ける設計を比較するため |
| 独自に検証する部分 | 両側の意味定義を根拠に、項目・関係ごとの喪失・追加・矛盾・比較不能を報告する契約と処理 | 既存の対応表の返却結果から、必要な監査結果まで何を補うか確かめるため |

HAPI FHIR と ROBOT は役割が異なる候補です。今回の選定は、両方の導入や組み合わせの確定を意味しません。

## 6. R1 の架空例に既存方式を当てた検討

以下は資料に基づく設計上の机上検討です。サーバーや推論器で動かした結果ではありません。臨床コードの正しい対応表を作った扱いにもしていません。

| R1 の例 | ConceptMap を比較基準にした場合 | 意味の比較で追加する必要があるもの |
| --- | --- | --- |
| 右側の骨折 → 骨折 | 入力が出力より狭いという意味関係を人が付けられる | 「右側が失われた」を得るための両側の定義と比較観点 |
| 骨折 → 右側の骨折 | 入力が出力より広い関係、必要条件を表せる | 原入力に右側の根拠がないことと、定義を解釈できない状態の区別 |
| 補助情報で右側を確認して追加 | 条件付き対応を記述する入口がある | 補助情報の情報源、入力時点、確認状態、条件を満たした根拠 |
| P は Q の下位概念、出力に Q を明記 | 対応の記録は可能 | 採用した含意の規則で Q を導き、情報追加と区別する処理 |
| 右側 → 左側 | 人が不適切な対応として記録することは可能 | 同一事象の同じ時点であること、左右の排他性、矛盾の根拠 |
| 未解釈のコード同士 | 対応が見つからない場合や対応なしの記録を扱える | 未解釈・未実装・根拠不足・明示的に対応なしという状態の区別 |
| A→B で左右が消え、その後 B→C | 各方向の対応を記録できる | 途中の喪失履歴と、原情報を利用して復元した場合の由来 |

ConceptMap の独自プロパティや拡張に、人が作成した項目別差分を格納する方法も比較対象に残します。「格納できること」と「意味定義から計算できること」を分け、事前に記述する作業量と自動化の効果を測ります。

## 7. 機械的な意味差分に必要な条件

実装仕様を確定する前に、比較する問いを固定する必要があります。作業案は、例えば「この事象は右側か」「これは本人の現在の確定した病態か」という有限の評価観点を用意し、入力側と出力側で何を裏付けられるかを比べることです。前節の論理差分研究は、その発想の参考になります。

- 問いの対象・時点・用途と、語彙・意味規則・版をそろえる。
- 両側で裏付けられる内容、入力側だけの内容、出力側だけの内容を分ける。
- 出力側だけの内容には、補助情報の裏付けと情報源を照合する。
- 反対の内容を裏付けられる場合と、単に裏付けられない場合を分ける。
- 定義不足、未対応の論理、計算の打ち切り、整合性の問題は比較不能として記録する。

これは MedDSL の検討案で、OWL や特定の推論器の採用決定ではありません。比較観点の外側にある差を検出したとは主張せず、「その観点・知識・規則での差分」として報告します。患者の実際の状態そのものを証明するものでもありません。

また、次の二つは別の処理です。

| 比較対象 | 目的 |
| --- | --- |
| コード定義・知識モデルの版の比較 | 同じコードの意味や含意が更新でどう変わったか調べる |
| 個別記録の変換前後の比較 | 原記録の主張が出力でも保たれるか、何が付加されたか調べる |

前者の既存研究を後者の解決済みの証拠にはしません。共通モデルへ取り込む際の近似を含めて検証します。

HAPI FHIR の基本テストを読めたことから、条件付き対応や全 R5 機能まで動作すると推定しません。実行環境・依存関係・ライセンスとデータの利用条件は R3〜R6 に持ち越します。

D02 の選定理由は、交換・対応管理と、意味・推論の責務を分けて検証できることです。対象資料が使えない、必要な条件を実装が扱えない、定義作成・運用負担が大きい場合に見直します。独自のコンパイラや包括的オントロジーを今作る決定はしていません。

## 9. 長期構想に対する設計上の示唆

openEHR の層の分離を参考に、安定させる情報モデル、専門領域の概念・制約、用途別のテンプレート、接続先固有の変換を分けて検討します。臨床ライブラリを標準化する対象には、名称だけでなく、操作の意味、入力情報、状態遷移、版、適合性を含める案です。これは今回の設計判断であり、操作不変を実証した結論ではありません。

AI 利用では、概念定義だけでなく「誰について、いつ、誰がどう判断したか」を扱う記録モデルが必要という要件を維持します。FHIR の Condition・Provenance、PROV を参照候補とし、AI の生成候補・導出根拠・人による確認状態をどこで表すかは R5 で決めます。JSON 化や用語コードの統一だけで性能が改善したとは主張しません。

MedDSL で確かめる独自部分は、こうした役割の間を接続し、変換と AI 向けの情報整形で失われた内容や追加された条件を同じ方法で説明することです。実現に必要な独自定義の量と、既存モデルを利用する効果を比較します。
