## 実装した範囲

`p1-request-draft-1` / `p1-result-draft-1` を追加し、`p1-finite-forecast-draft-1` の native handler で `query_forecast` を実行します。仕様実体の生バイトハッシュを handler に固定し、consumer の profile・仕様ハッシュ・操作と、各 artifact の版・ハッシュを照合します。未知能力や read_only の自己申告は、解釈する根拠にしません。

設計例の planned profile に付けた Markdown 草案のハッシュと、今回採用した機械可読 native 仕様のハッシュは別です。前者をそのまま実行可能とは扱わず、実行用 request は後者へ明示的に束縛しました。設計例の原ハッシュは変更していません。

有限モデル内の事象集合の積と、有理数の厳密な加算を実装しました。重みを正規化して修正したり、周辺確率を独立と仮定して掛けたりしません。同じ対象者でもモデル・標本空間・期間・報告文脈を暗黙に統合しません。

報告専用 snapshot に P0 の採用・訂正・human review を再利用し、元の生成元・未確認候補・原主張は入力に保持します。結果は入力・snapshot・artifact のハッシュと、台帳・assertion・review 参照を返します。原履歴の参照には原入力も保存する必要があります。確率1も forecast_probability のままで、臨床主張へ変換する演算・規則は持ちません。

未知能力、未解消の文脈内衝突、未採用、否定報告、未対応仕様、計算上限を分けます。未知能力は可視な保留・訂正済みの主張も対象とし、衝突は肯定・否定双方の根拠を保持します。共有予算で停止した一問の部分値は返さず、既に完了した別の回答は保持します。

相関の例では Pr(A)=Pr(B)=3/5、Pr(A∧B)=3/10 です。確率1の確認済み報告と、同じモデルの未確認AI報告を対にし、後者は undetermined/null。元の P0 臨床問い合わせが変化しないことも検査しました。

基本例の必要 steps は11で、0〜10の全打切り点で値が null、11で完了します。二問・複数 view での共通予算も検査しました。世界64・事象64・8事象連言の境界では646 stepsで確率1を返し、64 artifact/query/view と63 bit整数も受け付け、超過は停止します。

4096 bitの中間値制限は防護として実装しましたが、この入力上限ではそこへ到達する合法入力を作れません。高々64個の63 bit分母の積は4032 bit以内、正の部分和は高々64なので丸め前の分子も4038 bit以内です。従って4096 bit超過を実入力で再現して検証済みとはしません。上限を拡大するときにこの評価も改訂します。
