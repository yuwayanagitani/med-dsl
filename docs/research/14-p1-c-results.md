## 実装と認定の範囲

`p1-handover-draft-1` を追加し、参考モデルの検査、欠落を否定とする方針の診断、事象の改名・合成、射影の合成、旧処理系の可用性点検を分けました。P0/P1-a/P1-b の仕様・例・期待条件を維持しています。

参考意味では閉じた関係的一階式を有限モデルで評価し、与えられた反例候補が本当に source/target のモデルか確認します。含意を返す入口は文の明示、単項 Horn 導出、既知の存在規則に限定しました。証明も反例もない問いは unassessed で、非含意にしません。同じ signature・文集合の恒等変換だけは、全モデルが同じになる既知 template として認定できます。式の一致を実際の構造で確認し、報告ハッシュの一致を意味の証明にしないことも検査しました。

事象化→一対一改名では、実際の原・中間・最終 snapshot、完全な履歴、依存閉包、採用方針、翻訳済み問い合わせ範囲を検査します。改名以外の変更がないことと、原・新側の実行結果も照合します。認定の保証は**原履歴と、両計算が完了した P0 の支持契約**です。一般の一階推論、事象件数・同一性、新データ・方針変更、計算完了までを認定したものではありません。P1-b の有限照合票は従来通り not_certified で、新しい条件検査を行う別の処理です。

射影は値集合または列の選択、その後の符号化は canonical JSON の実際の復号確認です。第二段の認定を第一段の喪失へ流用しません。残った列だけを使う Q は範囲を限定して引き継げます。原情報の別添えを読む場合は sidecar_replay と明記し、利用可能なだけの別添えと実際に回答に使った情報も分けます。

## 上限と原保存

合成例は共有予算97 stepsで認定でき、96では最終認定を返しません。archive の確認と独立した合成は予算を共有し、100で完了、99では新側の途中票を返しません。全6操作の予算0も検査しました。P1-c は打切り時に要求全体を未評価として返し、途中のモデル判断・否定・認定を完全な結果にしません。

保存バイト列から復号した JSON にも通常入力の深さ・文字・型の検証を適用します。バイトのハッシュが正しくても P0 snapshot として解釈できなければ ready_to_replay にしません。深さ制限を base64 で迂回する入力や、通常入力では不正な文字列も検査しました。
