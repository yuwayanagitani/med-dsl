## 3. RV-05 の裁定

**裁定者の注記。** 利用者の指示により AI-001 が裁定を行いますが、RV-05 の指摘者と同一です。計画 §3 に照らし**独立した裁定とは数えません**。作成者側の回答は取得していません。確定には利用者（プロジェクト責任者）の承認が要ります。

### 3.1 問い

確認（review）の `recorded_at` が、対象の主張（assertion）の `recorded_at` より**厳密に前**の入力を、どう扱うか。現行版は構文上妥当として受理し、`as_of` が両方より後なら主張を採用して `supported` にします（再現：[KD01](../../examples/review/README.md)）。

### 3.2 実測した事実

| 事実 | 内容 |
| --- | --- |
| 契約・式 | P0 契約は「`recorded_at ≤ as_of` の主張とその時点までの確認記録だけを使う」とし、確認と主張の前後関係を定めない。PO04 の式も同様 |
| 同じ検査層の先例 | 訂正は「置換元より厳密に後に記録される」ことを検査し、満たさなければ `invalid_revision`（[validation.py:307-310](../../src/med_dsl/validation.py#L307)）。確認には対応する検査がない |
| 既存の例 | 固定済みの例（`examples/` の JSON から review 系列を除いた全部）の確認 274 件のうち、主張より前のものは **0 件** |
| 既存のテスト | 4 件が先行する確認を**近道として**含む。主張の時刻だけを未来へ動かして「未来の主張は見えない」ことを試す構成で、確認の時刻は元のまま（`test_p0_definitions.test_unconfirmed_and_future_memberships_cannot_trigger_rules`、`test_p0_ledger.test_future_unknown_record_does_not_block_historical_view`、`test_p0_query.test_future_modifier_does_not_affect_historical_view`、`test_p1_forecast.test_future_assertion_is_not_visible_even_with_earlier_review`） |
| 試験適用（隔離コピー） | `validation.py` に2行を足すと、機能テスト174件のうち失敗するのは上の4件のみ。4件は確認の時刻も未来へ動かせば元の意図のまま通る（確認済み）。handover 系のテストと p1-c の例15件は、P0 実体 hash の固定が崩れて失敗し、P1-d の評価器は `snapshot_mismatch` で停止する |

### 3.3 選択肢と論点

- **A 入力不正にする**（`review_precedes_assertion`）。
- **B 受理し、契約に「先行する確認も採用する」と明記する**。
- **C 受理するが、その確認を無効とみなして保留する**。

論点：
1. P0 の `recorded_at` は台帳への記録時刻で、観察の対象時点とは別です（P0 契約 P13）。確認は対象が台帳に記録された後にしか存在できません。先行する確認は時刻の因果が成立しない記録です。
2. 同じ検査層に、訂正の時刻順を拒否する先例があります。確認だけが検査されないのは不整合です。
3. 来歴が矛盾する入力で採用を確定すると、確認の本人性・時点を根拠に採用する設計（AGENTS.md の「不明な属性を補って確定しない」）に反します。拒否は原情報を消しません（入力側を直して再投入できる）。
4. 移行では、原確認の時刻を保ちたい場面が考えられます。ただし `recorded_at` は台帳への記録時刻であり、移行元の時刻は別の属性として保持すべきです（現行スキーマにはなく、`recorded_at` を書き換えて表すことも認めません）。
5. C は拒否と採用の中間状態と診断出力を新設し、意味の面積を増やします。B は PO04 の式に忠実ですが、式が因果を欠いているのが不足です。

想定される作成者側の説明（未取得）：契約が前後関係を要求していない／4件のテストが入力に含む。前者は契約の不足、後者は構成の近道であり、裁定を妨げないと判断します。

### 3.4 裁定

**A を採る。** 確認の `recorded_at` が対象の主張の `recorded_at` より厳密に前の入力は、構文が妥当でも**入力不正**とし、理由コードを `review_precedes_assertion`、`error_path` を `review.recorded_at` とする。**等しい時刻は許す**（時刻の解像度が1秒で、同時の確認があり得るため。訂正の厳密な後続とは性質が異なる）。

適用範囲：検査は P0 の入力検査を共有するため、P0 の問い合わせ・比較、事象の native 検査、予測の報告台帳、archive の解釈可否の検査に及ぶ。

**適用時期：現行版には適用せず、次の契約版（`p0-draft-2`、profile は `p0-positive-2` を推奨）で実装する。** 理由は二つ。(1) 現行の `p0-positive-1` は e73d4ba で固定・レビュー済みで、P0 の実体 hash が handover 系の認定に組み込まれているため、同じ版で変えるとレビューした基準が失われる。(2) 厳格化は、保存済みの archive が「解釈可能」かを変える（`audit_replay` の判定）ため、旧版の読み方を残す必要がある。現行版の挙動は KD01 で固定し、既知の逸脱として記録する。

PO04 の判定は「適合（現行版は既知の逸脱、次の契約版で解消）」とする。

### 3.5 適用時の手順（未実施）

1. `validation.py` の review 検査に次を追加する。

   ```python
   if review["recorded_at"] < assertions[review["assertion_ref"]]["recorded_at"]:
       raise Problem("review_precedes_assertion", "review.recorded_at")
   ```
2. P0 契約に規則を追記し、版を `p0-draft-2` とする。契約文書・P0 の5ファイルの hash が変わるため、`handover.py` の `P0_SPEC_SHA256`・`P0_RUNTIME_SHA256`、`handover_spec.json`、それに依存する p1-c の例（`consumer.profile_spec_sha256`・archive・段票・runtime 要求の hash）、各 manifest、P1-d の台帳を、新しい版として再固定する。**旧版（e73d4ba）の台帳と結果は残す。**
3. 上の4テストは確認の時刻も未来へ動かす（意図は変えない）。
4. KD01 の期待を `known_deviation.after_adoption` へ反転し、新規に「等しい時刻は許される」例を加える。
5. 初版の乱数照合（`fuzz_oracle.py` など）の生成器に、確認が主張以後になる制約を加えて再実行する。

### 3.6 暫定の運用

現行版を使う間は、入力側で `review.recorded_at >= assertion.recorded_at` を検査してください。現行版は先行する確認を採用します。
