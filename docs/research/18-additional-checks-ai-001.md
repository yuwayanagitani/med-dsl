## 1. compare 経路（喪失・追加・比較不能・根拠・予算の共有）

### 方法

独立オラクル（`reference_oracle.py`）は、PO04 の集合定義（可視・確認済み・訂正・採用・未知能力）、単項 Horn の不動点、全探索の結合を、実装の関数を使わずに書き直したものです。これで前後それぞれの回答を計算し、compare の各行を次のとおり導いて照合します。

| 項目 | オラクルの期待 |
| --- | --- |
| 比較不能 | 片側でも `conflict`／`unassessed` なら `incomparable`。差分・共通・根拠は `null`。理由に側付きの状態（`before_conflict` 等）。`incomplete` に列挙 |
| 喪失・追加・共通 | 支持された binding の集合の差・積。`supported` 以外は空集合。`undetermined`／`opposed` の行も「差分なし」と断言せず、状態を両側に返す |
| 順序 | 結果は query ID の順（入力の順に依らない）。各リストは binding の辞書順 |
| 根拠 | `lost_evidence` は前、`added_evidence` は後の台帳の参照。各根拠は採用された主張だけで構成され、**その主張・確認だけで同じ binding が支持される**（根拠の十分性を、最小の台帳で再計算して確認） |
| 文脈の対応 | 後側の文脈の別名と `context_map` の組（211ケース）で、`before_context_ref`／`after_context_ref` が正しい |
| 入力の hash・参照 | 各側の `snapshot_sha256`、`package_ref`、`ledger_ref` |
| 予算 | 左右で一つの予算を共有する。全予算で、完了した行は無制限実行と同一。完了できなかった行は差分なしにせず、`step_limit` を理由に挙げる |

400ケースの生成器は、前の台帳に削除・確度や符号の変更・新規の追加を加えて後の台帳を作り、台帳にある atom から問い合わせを作るので、前後の答えが重なります。衝突の経路を通すため、一部に確認済みの肯定と否定を共存させます。生成された2,120行（compared 1,768、incomparable 352）のうち、喪失あり27・追加あり11・共通あり33、`before_conflict` 111・`after_conflict` 116・`before_unassessed` 105・`after_unassessed` 121 と、各分岐を実際に通ります（テストが各分岐の回数を要求）。

### 結果

400ケースで実装とオラクルは一致し、**欠陥は見つからなかった**。そのほか、前後を入れ替えると喪失と追加が入れ替わる、同じ snapshot を両側に置くと差分がない、という性質も確認した。

27変異の検出：既存のテストと固定例が23件を検出し、**4件を見逃していた**（追加のテストが検出）。

| 変異 | 内容 | 見逃しの意味 |
| --- | --- | --- |
| C14 | 後側の `snapshot_sha256` に前側の hash を入れる | 結果が指す入力の hash を取り違えても検出されない |
| C16 | 理由コードの重複除去・整列をやめる | 比較不能の理由の形が変わっても検出されない |
| C19 | 返す `view` を空にする | 比較した参照時点が結果に残らなくても検出されない |
| C20 | 後側の `package_ref` を別の値にする | 同上（パッケージの参照） |

いずれも比較の**意味**（喪失・追加）には影響せず、結果の記録の完全性に関わる S2 相当の見逃しだった。追加のテストで閉じた。なお、`validate_compare` の7変異（文脈の再定義・対応の不一致・非単射・重複・未解決の対応、台帳参照の再定義、述語の再定義）は既存のテストが検出していた。

## 2. split_roles（誤った役割結合）

`split_roles` は、四役割を別々の事象から取る**既知の誤訳**です（`comparison.certificate` は常に不認定）。次の性質を200ケースで確認した。

| 性質 | 結果 |
| --- | --- |
| 旧（legacy）・正しい翻訳・`split_roles` の三つの結果が、独立オラクルの三つの期待（`split_roles` は役割ごとの値の直積）と一致 | 一致（ずれ 0） |
| 正しい翻訳の binding は `split_roles` に残る（喪失なし）。追加された binding が反例 | 成立。反例の集合はオラクルの「追加された binding」と**完全に一致**（過不足 0） |
| 反例の型（`truth_in_listed_model`、旧は偽、正しい翻訳は偽、誤訳は真） | 全反例で一致 |
| 反例があれば理由は `satisfaction_condition_failed`、なければ `unsupported_translation`。常に `not_certified` | 一致 |
| 事象が一つしかなければ役割を混ぜられず、反例は出ない | 30ケースで確認 |
| 正しい翻訳（`shared_event`）は反例を出さず、常に不認定（有限照合のため） | 80ケースで確認 |
| 打切り（行が積で増える）では、認定も反例の断定も出さず `unassessed` | 16ケース |

生成器は、別々の四つ組の値を混ぜた問い合わせを意図的に作る。200ケースのうち184が完了し、**88で実際に誤った結合が起き、すべて検出された**（16は資源上限で未評価）。

加えて、鎖の認定について：(1) 乱数200ケースで、認定は「すべての答えが完了（支持・未決・否定）」と一致（認定100超、不認定10超で空振りでない）。(2) **誤訳を主張する票**（`split_roles` の翻訳後 Q 範囲の hash を、両段で整合させて入れた票）は、段の接続検査を通っても、実体からの再計算で `stage_1.target_scope_sha256` と `stage_2.source_scope_sha256` が不一致になり不認定になる。

### 検出力（変異検査）

役割結合に関わる9変異（native の事象化で役割ごとに別の事象にする W1、全関係で一つの事象を共有する W2、内部変数を公開 binding に漏らす W4、`split_roles` を正しい翻訳に変える S2、反例の型・理由・認定・出力の取り違え S7〜S11）はすべて検出された。**S7（`split_roles` なら常に `satisfaction_condition_failed` にする）は、追加のテストだけが検出した**（既存のテストは見逃していた）。

### 限界

- `split_roles` は事象ごとに四つの変数を持つので、行が積で増える。大きな履歴では上限に達して `unassessed` になり、診断として使えない（上の16ケース）。診断は小さな例のための道具である。
- 反例は「指定した有限の履歴の listed model」の意味での真偽で、任意のモデルでの誤りの証明ではない。
