## 3. 後付けで分かったこと

後付けの作業そのものが、契約の設計を点検した。

1. **host という層が要る。** 引き継ぎの5操作は、schema・profile・仕様・P0 実体の固定を共有する。操作ごとの宣言だけでは、共有する名前の所有者が決められず、`HOST` クラス（操作を持たない共有の前段）と `BASE`（基底）を契約に加えた。設計（19）の分類は R1〜R5＋合成だった。
2. **`embedded_in` は拡張ごとではなく、pin ごとに和で見る。** events の仕様 hash は、events 自身の宣言と host の宣言の両方で pin される。埋め込み先の漏れは、pin を宣言した拡張すべての和に対して検査する（最初の検査が、host 単独では漏れていると報告して分かった）。
3. **名前を組み立てる実装は、名前空間で宣言する。** events は述語の URN を `"urn:med-dsl:events:role:" + 役割` で作る。文字列として現れないため、最初は `owned_name_not_found` で拒否された。末尾が `:` の名前を名前空間として所有する規則を加えた。
4. **未宣言の読み取りがあった。** 最初の宣言で、`p1-replay` が鎖の認定を読むことを書き落としていた。コードを読んで気付き、上の非干渉の検査が同じ誤りを検出することを確認して、宣言を直した。**宣言は作者の主張なので、検査で突き合わせる仕組みが要る**ことの実例。
5. **防護例のない義務の分布。** 24件の内訳は、共通の義務 15件（`K-RES` 8、`K-STOP` 4、`K-INV` 3）とクラス固有 9件。宣言の `guard_gap` に書かれた理由で分けると次のとおり。
   - **テストで検査していて、例ファイルがない（12件）**：予算・上限の境界（`K-RES` 8、`K-STOP` のうち 3）と、範囲外の問いで認定が出ないこと（鎖の `COMP-2`）。例を作ると境界値の構成が大きい、または乱数照合が担っている。
   - **別の防護例またはテストが担う（6件）**：`K-INV` 3（認定が定義パッケージだけを読み新しい出力がない、`COMP-1` の防護例が担う、全例の入力保持をテストで検査）、host の `K-STOP`（各操作の拒否例が担う）、`p0-definitions` の `R1-3`（`R1-1`・`R1-2`・`R1-4` が担う）、参考意味の `R3-4`（`R3-1` の防護例が担う）。
   - **構造の性質で、拒否する入力の例がない（3件）**：事象化の `R3-4`（新理論の範囲）、基本予測の `R2-2`（報告専用の固定 package しか検証に渡さない）、鎖の `COMP-3`（この鎖に損失のある段がない）。
   - **手作業の導出（1件）**：事象化の `R3-3`（被覆）。反例の検査は参考意味が担い、事象化自身は有限照合だけ。宣言の上で、証拠が弱い義務として見えるようになった。
   - **該当なし（2件）**：参考意味の `R3-5`（履歴を持たない）と `R3-6`（恒等の翻訳で新しい名前を導入しない）。これらは「証拠がない」ではなく、義務が空になる理由を宣言に残したもの。

   「別の防護例が担う」「該当なし」の判断は作成者の主張で、独立の確認は受けていない。
6. **列挙はモジュールの粒度で過大になる。** `handover.py` 一つに引き継ぎの全操作があるため、events・projection・reference の変更は host とその全操作に及ぶと列挙される（漏れではなく過大）。操作ごとの実装の分離で改善できるが、挙動を変えるリファクタリングなので P2-a では行わなかった。

## 4. 設計（19）からの変更

| 設計 | 実際 | 理由 |
| --- | --- | --- |
| 後付けは6件（S1/S2、forecast、events、鎖、射影、参考意味） | 10件（基底、host、欠落の診断、可用性の点検を追加） | ディスパッチされる全操作に所有者を決めるため。host は §3-1 |
| 義務の「負例」 | 「防護例」（`refusal`／`non_conversion`／`boundary`） | 「確率1でも supported にしない」など、拒否ではなく変換しないことを守る例を含めるため |
| 拡張ホストの分離を P2-a に含める | 行わない | X03 は、handler の差し替えで実現できた。分離は挙動を変えないリファクタリングで、固定ファイルを広く変え、再固定を要する。宣言と検査を先に固定し、必要は P2-b の前に判断する |
| 証拠の強さ4段階 | 5段階（`hand_derivation` を `finite_check` と `checked_native_template` の間に追加） | 手作業の導出（S1/S2 のモデル拡張、事象化の被覆）を、有限照合と区別するため |

## 6. 限界と次

- 宣言と検査は、意味の正しさを検査しない（実行契約 20 の §7）。独立の確認者は未割当で、`independent_review` の主張は拒否される。
- 宣言・`tests/p2`・`check-extensions.py` は P1-d の固定対象に含まれない（固定対象は 169 → 170 ファイルで、増えたのは `src/med_dsl/extensions.py` だけ）。宣言の改ざんや取り違えは、固定された hash では検出できない。固定対象に加えるかは P2-b の前に判断する。
- 防護例を実際に評価する登録は、**今ある例**が宣言どおりの結果を返すことを確かめる。ゲートを壊す実装の変更を検出できるかは別で、`extensions.py` 自体は変異 37件で確かめたが、既存の handler の防護例が各ゲートの変異を検出するかは、P2-a では測っていない（RV-01 の変異検査は P0/P1 の handler について実施済み。[17](17-internal-run-ai-001.md)）。
- X04・X05・X08〜X12・X14 は P2-b 以降。X05（回答型の暗黙変換がない）の機械的な検査は、回答型の宣言と結果の schema の突き合わせが要る。
- 次は P2-b：パイロット「概念の分割」（[19 の §7](19-p2-design.md)）を、この契約に沿って設計・実装する。最初の作業は、新しい意味（候補集合と情報要求）の宣言を書き、義務を手作業で導くこと。実装に入る前に、利用者の確認を取る。
