### 非干渉（X03）の無効化の方法

登録表が関数の参照を持つようになったので、モジュールの属性を差し替えるだけでは無効にならない。拡張を不活性にする方法を、**宣言した実装モジュールが定義する全関数を、他のモジュールが import した束縛も含めて差し替え、ホストの登録表（`host.SURFACES`、`handover.OPERATIONS`）の該当の項目も差し替える**形に変えた。これは、以前の「拡張ごとに差し替える関数の表」より厳しい：宣言したモジュールの関数のうち、宣言に現れない依存先から呼ばれるものがあれば、非干渉の破れとして見つかる。結果は以前と同じ（8 拡張を無効にしたとき、その拡張と依存先に属さない例の結果は変わらず、属する例は変わる）。宣言の誤り（`p1-replay` が鎖を読むことの書き落とし）が検出されることも、新しい方法で再確認した。

### 限界

- 登録の辺を辿らないので、ホストが操作の関数を**実際に**使う逆向きの読み取りは、列挙では見えない。非干渉の検査（無効化）が見るが、ホスト自身が持つ例がなければ見えない。
- `__init__.py` が再 export していた名前（`PROFILE`、`Problem` など）を削った。リポジトリ内に使う箇所はなかった（使われていたのは `evaluate` だけ）が、外部の利用者がいればここは契約の変更になる。
- `examples/review/` の `gate`（例：`handover.py:176`）の行番号は分離前の位置。固定した例を書き換えないため、対応表を [examples/review/README.md](../../examples/review/README.md) に追記した。

## 2. 防護例の追加

### 対象

P2-a で防護例のなかった義務 24 件のうち、拒否・境界の入力を構成できる 21 件に防護例を付けた。新しい例 35 件を [examples/p2/](../../examples/p2/README.md) に置き（台帳つき。別の分母）、事象化の R3-4 だけは既存の例（`p1-b/shared-key`：同じキーの 2 つの主張が別々に保持される）を引いた。

| 義務の種類 | 付けた防護例 |
| --- | --- |
| 予算の境界（`K-RES`、8 拡張） | 各拡張の既存の例を、予算だけ変えた対：完了に要る最小の steps n の **n−1 で止まる**／**n で完了する**（上限を厳しくしすぎない）。参考意味には式の深さの上限（16）の境界も |
| 停止（`K-STOP`） | 定義：予算 0（追加が空でも）／鎖：未知の能力で認定しない／ホスト：未登録の操作・consumer の操作・profile／参考意味：有限領域の探査は未対応・式の深さの上限 |
| 不変条件（`K-INV`） | 定義：台帳を受け付けない／鎖：確認のない AI 候補が支持にならない（未決のまま両計算が一致）／ホスト：打切りで認定票・部分の報告を出さない |
| 鎖の範囲（`COMP-2`） | 範囲外の問い（事象の同一性）を旧の問いの認定に含めない |
| 予測（`R2-2`） | 任意の package・報告専用の述語以外を受け付けない |
| 参考意味（`R3-4`、`R3-5`、`R3-6`） | 新理論が文を一つ追加するとき被覆を真にも偽にもしない／台帳を受け付けない／宣言した語彙にない述語を持ち込めない |

**欠落として残る 3 件**（拒否する入力を構成できない。理由は宣言の `guard_gap`）：定義の `R1-3`（旧モデルの拡張は構文の十分条件 `R1-1`・`R1-2`・`R1-4` で保証され、独自の拒否例がない）、事象化の `R3-3`（被覆は手作業の導出で、反例の検査は参考意味が担う）、鎖の `COMP-3`（この鎖に損失のある段がない）。

### 作り方

期待結果は、ゲートの意味から**手で指定**し、処理系の出力から生成していない（例外は予算の境界の n で、無制限の実行の `steps_used` を測った）。鎖の入力は、変更した履歴から端点・範囲の宣言を作り直す必要があるため、実装の事象化・改名・端点の計算を**入力の構成にだけ**使った。35 件のうち最初の 33 件は、最初の実行で期待が全件一致した。一致しただけでは検出力の証拠にならないので、次の変異検査を行った（残りの 2 件は変異検査の結果で追加した）。

### 検出力（変異検査）

防護例を付けたゲートごとに実装を壊し（27 件）、意図した例が失敗するかを調べた。あわせて、既存の開発テスト（231）とレビュー系列（52）が同じ変異を検出するかも記録した。変異は、予算の課金の削除（9）、ゲートの条件の緩和・削除（11）、認定・採用の条件の変更（4）、予算の定義の変更（2）、停止時の応答の形（1）で、**作成者が防護例の対象に合わせて選んだ**もの（網羅的な変異演算子の集合ではない）。P0 実行体のファイルを変異させるときは、変異後の hash に再固定した。対照（変異なし）は失敗 0。

| 結果 | 件数 |
| --- | --- |
| 意図した防護例が失敗した（検出） | **27 / 27** |
| 既存の開発テスト・レビュー系列も検出した | 17 |
| **既存のテストが見逃し、防護例だけが検出した** | **10**（欠落の診断・改名・射影・参考意味の課金、式の深さの下側の境界、有限探査の未対応、ホストの操作・consumer の操作・profile の検査、参考意味の語彙の検査） |

検査で分かったこと：

1. **定義の初期の課金が、最初の例では守られていなかった。** 「予算 0 は、追加が空でも未評価」という初期の課金（`definitions.py` の最初の `budget.tick()`）を外しても、追加が空でない例は後の課金で止まるので、予算 0 の例が失敗しなかった。追加が空の例（予算 0 と 1 の対）を足して検出できるようにした。
2. **等価な変異が一つあった。** 鎖の `certified = complete and not outside` の `and not outside` を外しても、どの検査も失敗しない。範囲外の問いがあると事象化の比較の状態が `partial` になり、`complete`（全比較が `matched`）が偽になるので、`not outside` は冗長（多重の防御）。代わりに範囲外の問いの集計（`outside`）を壊す変異で、`chain-out-of-scope-query` が検出することを確認した。
3. **重複した防御がある。** 予算 0 を「無制限」とみなす変異（`Budget.tick`）でも、鎖は止まる。内側の P0 の問い合わせ（`query.py`）が、予算 0 を未評価として止める独立のゲートを持つため。そのため鎖の予算 0 の例は、停止時の応答の形（`incomplete: ["request"]`、認定票なし）を壊す変異で検出できることを確認した。個々のゲートが単独で守られているとは限らない。
4. **検査の環境の誤りを一度出した。** 変異した作業ツリーの複製が git のリポジトリでなく、既存テストの一つが `git rev-parse` で失敗するため、「既存テストで検出」の列が全変異で誤って検出になった。対照の変異を加えて気付き、環境を直して全変異をやり直した。結果は上の表の値。

### 限界

- 変異は作成者が選んだ 27 件で、防護例が検出できない退行が他にないことは示していない。
- 防護例の期待は作成者が手で指定した主張で、独立の確認は受けていない。
- 防護例のない義務 3 件の理由（「拒否する入力を構成できない」）は、構成できないことの証明ではなく、作成者が試みた範囲の判断。

## 3. 宣言の固定

### 固定したもの

共通 manifest（lock、`examples/p1-evaluation/manifest.json`）の対象に、次を加えた（評価器 `evaluate-p1-d.py` の `EXTENSION_PATTERNS`）。固定対象は **170 → 248 ファイル**（新しい実装モジュール 5 を含む）。

| 追加 | ファイル数 |
| --- | ---: |
| `extensions/*.json`（宣言 10 と索引） | 11 |
| `examples/p2/*.json`（防護例 35 と台帳） | 36 |
| `examples/review/*.json`（宣言が引くレビュー系列の例と台帳） | 15 |
| `tests/review/*.py`（宣言が引く検査と独立オラクル） | 7 |

| 実装モジュール（`host.py`、`handover_common.py`、`chain.py`、`absence.py`、`replay.py`） | 5 |

**範囲の決め方**：宣言だけを固定しても、宣言が根拠として引く防護例・検査・オラクルが差し替えられれば、宣言の主張は黙って崩れる。そこで「宣言と、宣言が引くものすべて」を固定対象にし、それを**テストで保証**した（`test_the_lock_pins_the_declarations_and_everything_they_cite`：実装・仕様・契約・pin・評価の例・検査・オラクル・防護例のうち、固定対象に載っていないものは、監査スクリプト 1 件だけ）。

**例外**：`scripts/research/audit-preservation.py` は載せない。固定対象の sha256 を定数に持つので、載せると自己参照の循環になる（`test_the_audit_script_is_outside_the_lock_because_it_holds_the_lock_hash` が、この理由が今も成り立つことを検査する）。固定対象の hash が変われば、固定対象に載る `tests/audits` が検出する。

**分母は変えていない**：P1 の 20 条件・80 JSON・417 必須パス、P0 の 22 条件・37 JSON・221 必須パスは同じ。レビュー系列と防護例は、宣言が根拠として引く実体として載るだけで、評価の分母（`SUITES`）には入らない。「レビュー系列は固定対象に載らない」という書き方だったテスト（`tests/review/test_review_negatives.py`）は、意図（分母に入らない）に合わせて「分母は 4 系列だけ」に直した。

### 効果と限界

- 宣言、防護例、検査、オラクルのどれを変えても、固定対象の再固定（明示的な `--create-snapshot`）が要り、評価器の `preflight` が不一致を拒否する。
- 固定対象は同じリポジトリのファイルなので、**改ざんを防ぐものではなく**、変更を見落とさないための関門。外側の錨は、固定対象の hash を持つ監査スクリプトの定数だけで、外部への記録（独立の確認者による固定）は未実施。
- `certifier`（認定票に付く実装の束の hash）は、従来どおり `src/med_dsl/` の `*.py` と `*.json` だけから計算する（24 ファイル）。宣言や例は含めない。
