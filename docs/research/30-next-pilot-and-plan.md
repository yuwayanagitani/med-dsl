## D16：次は候補B「有効期間つきの主張」

次のまとまりを **P2-e** とし、候補B「有効期間つきの主張」を設計・試作・評価する順序にします。最初の具体的な作業は、時間の意味と保存条件、反例、受入条件を設計することです。今回はその選定と作業順までを記録し、runtimeは変更しません。

| 比較軸 | B：有効期間つきの主張 | C：単位つきの数量 |
| --- | --- | --- |
| 既存契約に対する問い | 採用・訂正・可視性と期間の関係を、旧意味を変えずに追加できるか | 新しい値の型・単位・換算・比較を、基底の状態と分離できるか |
| これまでとの違い | 時間に依存する解釈を扱い、現在の停止・採用の契約に不足がないかを調べられる | 型付きの読み取りモジュールとして、既存の予測等で得た方法を適用しやすいと見込む |
| 将来の入力・出力分離との関係 | 入力した時刻と主張の対象期間を保持し、出力先の時点の要求へ結ぶための基盤になる | 数量の意味を保持して、接続先が異なる表記・単位を求める場合の基盤になる |
| 実装規模と不確実性 | 大きい。設計を先に行い、初回の断片を限定する | 比較的小さいと見込む。ただし正確な値・丸め・単位の意味の設計は必要 |
| 今回の順位 | **次に着手** | Bの結果を受けた次の候補として保持 |

Bを優先する理由は、機能の実装量よりも、**現在の拡張契約が異なる種類の意味追加に耐えるか**を研究したいためです。時間を扱う機能を増やすことだけを成功条件にせず、前提・保存・改訂・停止・併用の義務を、契約から導けるかを評価します。Cを不要と判断したわけではありません。

## P2-eで最初に設計すること

現在のP0には、主張・確認の `recorded_at`、参照時点 `view.as_of`、文脈の単一対象時点 `context.effective_at` があります（`ledger.py`・`validation.py`）。今回の対象は、これらの既存項目を別の意味へ読み替えることではなく、**主張が対象とする期間と、いつその主張を利用できたかを区別する拡張**です。

| 設計項目 | 決めること・先に作る反例 |
| --- | --- |
| 二つの時間の区別 | 記録・確認が見える参照時点と、主張の対象期間を区別する。後から記録された情報が過去の参照時点へ漏れない例を作る |
| 期間の意味 | 区間の境界、未知・未指定・終点なしの区別を定める。未指定を全期間に有効と補完しない |
| 採用と期間の順序 | 採用してから期間を絞る操作と、期間を絞ってから採用する操作が異なる例を作る。期間を限定した訂正が、元の主張の期間外に与える影響を決める |
| 否定・衝突 | 期間外・期間不明を明示否定にしない。肯定と否定が異なる期間にある場合と、重なる場合を区別する |
| 旧意味との関係 | 有効期間を問わない旧要求の観測を維持し、期間を参照する新しい問いと型を分ける。新しい結果を旧状態へ暗黙に変換しない |
| 拡張契約への適合 | 所有、依存、意味クラス、義務、未知能力への停止、再検証範囲を宣言する。既存クラスに収まらない場合は不足と変更理由を記す |

例として、ある架空の主張が10月1日〜5日を対象にし、10月8日に初めて記録・確認された場合を使えます。10月6日時点の知識でその主張を利用してよいか、10月9日時点の知識で10月3日について何を答えられるか、10月6日について答えがないことを否定と扱ってよいかを、別の問いとして先に整理します。これは試験用の設定で、既存の時刻規則を変更する仕様ではありません。

初回の断片は、明示した有限の期間、単一文脈・個体のground主張、対象時点についての問い合わせを出発案とします。UTCと半開区間を用いる案を比較し、最終的なschema・回答型・境界値・課金点は意味設計の後に固定します。時間の持続を自動推論する規則、一般の時間論理、未来の予測、医学的な有効期間の推定は初回の対象に含めません。
