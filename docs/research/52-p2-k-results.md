新 profile は `p2-validity-refinement-draft-1`、操作は `probe_refined_temporal_literal`、台帳は `p2-refinement-ledger-draft-1` です。**精密化は元の記録を書き換えず、記録についての新しい種類の記録（`refinements`）**で、固有の人の確認（`refinement_reviews`）が、対象の記録と精密化自身の内容 hash を拘束します。効くのは、記録と確認の両方が参照時点以下で、`confirmed` かつ人の確認があるものだけです。同じ記録の適格な精密化が、異なる区間なら競合として止まり（後勝ちにしない）、同一の区間なら一つにまとまります。

精密化が確定すると、期間不明だった記録は、精密化した区間の内側でだけ適用されます。区間の外では適用されず、否定にも全期間にもなりません（`neither`）。停止の順序は、未知の能力 → 期間の阻害（不明・未指定・競合）→ 精密化後の区間に対する訂正の包含の矛盾 → 判定です。

## 4. 分かったこと

1. **意味の継承を宣言する枠がなく、実装を共有できなかった。** 精密化を足すには記録の新しい種類が要り、既存の P2-e の台帳のスキーマは拡張できないため、新しい台帳スキーマと、P2-e の意味を再実装した専用モジュールが要りました（検証と選択の大半が構造として重複）。契約の宣言（`depends_on`・`reads_extensions`）には、「P2-e の意味を継承する」という関係を書く欄がありません。継承が崩れていないことは、**精密化のない P2-k の要求を P2-e の実装に流して、21,920行を比較する差分の検査**で確かめました。この検査は宣言には書かれていない義務で、仮説 H8 の根拠になります（[49](49-extension-principles.md)）。
2. **記録についての記録は、既存のクラスで表せたが、固有の義務は個別に要った。** 契約のクラス（R5）と必須欄は満たせました。しかし、確認が対象の内容を拘束すること（RF-2）、精密化の対象と区間の限定（RF-9）、精密化と部分訂正の包含を参照時点ごとに検査すること（RF-11）は、R5 の必須欄から出てこず、個別義務として設計しました。H2（義務の大半は能力を問わない主題、意味固有は少数）と矛盾しませんが、意味固有の4件は、記録の期間という属性を別の記録が確定する、という新しい意味に固有でした。
3. **包含検査を静的にすると過去の参照時点が壊れる。** 精密化の有無は参照時点で変わるので、訂正の包含を入力全体で検査すると、未来の精密化が過去の参照時点の結果を変えます（RF-D7・RF-L1）。包含を参照時点ごとの診断にして、この問題を避けました。
4. **M1 と M2 は区間の外側で異なる。** 精密化を記録の期間の割当（M1、採用）として表すと、区間の外側の問いが `neither` で完了します。部分訂正（M2、採らない）で表すと `unassessed` のままです（CT01）。契約が「記録の期間を後から別の記録が確定する」枠を持つかどうかは、この断片では、専用の台帳の種類として持たせることで解決しました。一般の枠にしたわけではありません。
5. **競合は永続する。** 異なる区間の精密化が二つあると、解消する操作がこの断片にないため、阻害が続きます（RF-12）。情報要求は `resolution_supported: false` で、解消できるとは偽りません。
