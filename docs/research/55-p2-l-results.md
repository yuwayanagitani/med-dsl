## 3. 分かったこと

1. **比較の正規化が、符号化の中の hash を見ていなかった。** 初回の比較では、期待が変わった入力が161件と出ました。表示の artifact は、canonical JSON の base64 符号化を結果に持ち、その中に仕様の hash が含まれます。64桁の16進の置換では、符号化された文字列の違いが hash の違いに見えません。符号化を復号して中身を正規化するように比較器を直すと、期待の差は宣言した6件だけになりました。**hash を含む符号化の値は、hash の文字列としては見えない**ことを、版の比較器の前提として明記します。
2. **派生した hash があるので、置換では再固定できない。** 確認が拘束する内容の hash（記録・数量・確認の内容の hash）は、仕様の hash を含みます。再固定には、各系列の生成器（派生した hash を計算する）が必要で、**生成器を旧版と同じ時点で保持する**ことが版の手順の前提になります。
3. **宣言の防護例の期待値も、改訂の影響を受けた。** 期間つき数量の宣言の防護例（TM-7）が、`u_third` の旧い値 1/3 を期待していて、改訂の後に登録が拒否されました（`guard_outcome_mismatch`）。登録時の防護例の評価が、改訂の取りこぼしを検出しました。これは `affected()` の列挙にない、第二の依存です（宣言の防護例 → 例の内容）。
4. **生成器が仕様の hash の複製を持っていた。** 期間つき数量の生成器が、測定の仕様の hash を文字列で埋め込んでいました（他の拡張の確認を流用する対照の入力のため）。旧い hash の文字列を探す点検で見つかり、仕様から読む形に直しました。`affected()` は生成器の内容を宣言から知らないので、列挙できません。
5. **継承の差分の義務（VR-1）は、現在の宣言の書式で書けたが、機械的な継承の検査にはならない。** 義務として宣言し、防護例（改訂した値、追加した値）と検査（単位表の差分、版をまたぐ差分）を結べました。ただし、義務が「旧版との差分」を指すことを、registry は理解しません（検査の名前を引くだけ）。[49 の H8](49-extension-principles.md)（継承を宣言する枠がない）に、版の更新の側からの一つの根拠が加わります。
6. **意味の変更が小さくても、固定の連鎖は大きい。** 意味を変えたのは単位表の2行ですが、仕様5・モジュール5・実行例687ファイル（manifest 5件を含む）・宣言5と索引・台帳が書き換わりました。hash の固定が、変更の見落としを防ぐ一方、変更の局所性を保証しないことを示す測定です。

## 4. 検査の強さ

- **比較器の変異**：再生成した入力の比較の判定14件（G01〜G14）と、符号化の正規化1件（C11）を、検査器の変異の表に追加しました。最終版で、G01〜G14（14件）・C01〜C11（11件）・V01〜V07（7件）・E01〜E14（14件）の計46件を実行し、**46件すべて検出**しました（変更した部分と新しい部分の再実行。予算の検査器 B01〜B16 と記録の照合 R01〜R08 は、コードを変えていないので再実行していません）。最初の実行で G13（入力件数と記録の照合）が見逃され、その検査を足して検出されました。
- **単位表の検査（VR-1 の単一の木の部分）**：現在の単位表が、draft-1 の表に宣言した変更だけを加えたものであることを、native 仕様を読まない独立した表と照合します。
- **実行例**：手で導いた期待（6件の変更、Q25）を含む5系列（683件）は、再生成の最初の評価で全て期待と一致しました。別計算（数量・測定・期間つき数量の別計算）の単位表も、宣言した改訂に合わせて更新しました。

## 6. 限界と次

- 改訂の対象は、架空の単位表の2行です。計算規則の改訂、依存の追加・削除、拡張の削除、profile 名を変える方式、複数の版の同居は未実施です。
- 継承の差分は、旧入力が存在する範囲の比較です。旧入力に現れない振る舞いは比べられません。
- 宣言の書式は変えていません。継承を表す欄の追加が要るかは、H8 の根拠として残しました。
- 次の候補は、C2（縦断比較）です。着手前に利用者の確認を取ります。独立確認は将来の英語の別リポジトリで行います。
