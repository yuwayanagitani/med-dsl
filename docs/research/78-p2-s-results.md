## 4. 実装の最中に見つかった誤りと直し方

- **版の記録の作成が止まった（実装の副作用）**：版の記録の作成器が、宣言にない結果の差として `p2-temporal-measurement/o12.json` の `error_path` を報告した。`ref` を条件つきの必須にした新しい検査が、欠落を `record.observer.ref` と報告していたが、旧版と他の検査（`fields()`）は入れ物の `record.observer` を報告する。理由と状態は同じ（`invalid_input`／`missing_field`）で、期待は経路を固定していなかったため、テストでは見つからなかった。**比較器が設計の宣言（`observer` の必須化）と無関係な診断の変化を見つけた**例。新しい検査の報告を入れ物のパスに直した（`c586272`）。経路を宣言に足して許容する選択もあったが、意図した変更でなく、旧版との一致を保つほうが小さい変更だったため、実装の側を直した。この直しの後で版の記録を作った。
- **履歴の検査の期待の誤り**：S9 の「拒否は `invalid_observer`、拒否が受理より多い」を履歴の検査に書いていたため、測定（`invalid_observer` 2件）と合わなかった。検査を、予測でなく成り立つ性質（`unknown` を含む入力の受理 0、受理は `unknown` を含まない入力だけ、`unknown` を含む入力は受理より多い）に直し、理由の分布を版の記録の測定値に加えた（`unknown_observer_first_reason`）。予測の外れは §2 に残した。
- **実装の誤り**：上の1件のみ。設計77の手指定の期待（O20〜O23、O73、N03 の2件、O04 の変更）は、最終の例の期待と一致している（文書の値と例の期待を突き合わせた）。ただし 76・77 は実装と同じコミット（`fe420cb`）で履歴に入れたため、「実装前に固定した」ことは履歴からは示せない。

## 5. 分かったこと

1. **任意の項目を必須にする更新でも、意味の局所性は保たれた。** 旧入力762件は黙って再解釈されず（拒否703・同一59・変更0）、旧い pin を置換しただけの入力は18件全て欠落した必須項目で拒否された。移行は「欠落に明示の `unknown` を足す」だけで、期待を個別に変えたのは1例（O04）だった。一方、書き換わったファイルは820件と、任意の項目を足したとき（P2-r の813件）とほぼ同じ規模だった。
2. **必須にすることは、答えの強制でなく、「聞いたが分からない」と「聞いていない」を分けることだった。** `unknown` は観察者を推測せず、Provenance の agent・依頼・流れを変えない。ただし `unknown` の細分（聞いていない／聞いたが分からない）は扱っていない。
3. **比較器は、要求の側の変更を小さな拡張で宣言でき、宣言にない差も見つけた。** 宣言の種類 `required_field` の追加は26行で、書式は不変。移行の差を許す一方で、宣言にない `error_path` の変化を失敗にした（§4）。

## 6. 検査の強さ

- **観察者の必須化**：P2-i の全数（観察者 欠落／`unknown`／human／device × 訂正の鎖の2記録、記録の hash が観察者ごとに異なること）、不正な観察者の全数、確認の後の書き換え。P2-o の受け渡しの全数（操作の観察者 欠落／`unknown`／human／device × 確認の操作の観察者）。P2-q の全数。いずれも別計算または独立な計算と比べた。
- **変異（テストに組み込んだもの）**：P2-i は、観察者の種類の検査の削除、`record_observer` を出さない、`unknown` に `ref` を許す、の3件（種類の検査は `unknown` を含む形に更新）。P2-o は、台帳へ渡さず `unknown` で置き換える（補完に当たる）、根拠に出さない、の2件。全件検出。
- **変異（設計77の§6のうち、テストには組み込んでいないもの）**：使い捨ての作業木で一度だけ試した。(1) 欠落を `unknown` で補う（P2-i）、(2) `unknown` を `ref` が必要な種類と同じに扱う（P2-i）、(3) P2-q が `unknown` を観察者のない場合として正規化する行の削除、(4) 確認の操作が任意の `observer` を受理する（P2-o）。いずれも既存のテストが失敗して検出した（(3) は多くのテストが `ref` の参照で異常終了するという粗い検出）。コミットした検査ではないので、再現するには変異を手で当てる。設計の「`unknown` で依頼を出す」変異は試していない。
- **版の手順**：V1〜V8 を履歴の検査9テストで確認した。比較器の単位テスト5は、宣言どおりの報告が通ること、宣言外の要求・期待・結果の差と、置換の拒否の理由の食い違いが報告されること、宣言のない記録が従来どおり厳しいことを確かめる。
- **比較器の変異**：G01〜G05・G10・G15・G16 と対照 Z0 を再実行（比較器を変えたため）。全件検出、対照は失敗0。

## 8. 限界と次

- **必須にする更新は、1つの項目（`observer`）の1回の実演**です。項目の意味の変更、削除、複数の項目の同時の更新は試していません。
- **移行は有限の旧入力（762件）と生成器の既定の変更**に基づきます。旧入力が行使しない新版の変更は旧入力の比較では見えません。一般の移行の正しさの証明ではありません。
- **`unknown` は「観察者が分からない」の一つの値**で、聞いていない・聞いたが分からない、の細分、観察者の同一性・資格・履歴は扱いません。補完の層（画面など）も範囲外です。
- **比較器の宣言の照合は項目の名前で行い、粗い**（F32）。
- 設計者・実装者・検査の作成者が同一で、独立確認はありません。
- 次の候補は、revision の entity と activity の符号、CPC の版の監査、複数の出力先への射影の拡張です。着手前に利用者の確認を取ります。独立確認は将来の英語の別リポジトリで行います。
