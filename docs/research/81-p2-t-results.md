## 4. 分かったこと

1. **訂正の関係は、下位を変えずに運べた。** P2-q の行を書き換えず、`coding` を足すだけで、向き（target＝新しい版、entity＝古い版）・同一性（記録の参照と独立に計算したハッシュ）・多重度（記録ごとに一つ）を保てた。連鎖は直接の前の版だけを運び、全体と訂正の理由は運ばない。
2. **訂正の関係を運べるかは、訂正者が分かるかに依る。** Provenance は agent が必須（1..*）なので、観察者を不明と明示した（P2-s）訂正は、人が確認していても関係を運べない。これを黙って落とさず `no_agent` と区別し、確認の項目に付けて埋め合わせもしなかった。576要求の全数では、訂正を含む384要求のうち、`revision` を求めて確認者の型を宣言した96要求で、運べたのが80、運べなかったのが16（観察者が不明で出自が AI でない場合）だった。
3. **活動の符号は、構造の検査の外にある。** 束縛が Example なので、符号の集合は限られず、内容を検査できない。検査できるのは、種類ごとに宣言が使われたか、代用されなかったか、運べなかった種類が報告されたかの規則だけである。一方、`entity.role` の符号は必須の束縛で、R4→R5 で `derivation` が消え `instantiates` が加わった。役割を宣言に預けず、拡張が事実の表（出典のハッシュと目印の語）に結んだ `revision` に固定したので、R4 の語は静的に拒否される。

## 5. 検査の強さ

- **全数**：記録の場合（原本／訂正1件／訂正2件）×観察者（不明／人／装置）×出自（観察／AI）×確認者の型の宣言（あり／なし）×活動の宣言の部分集合（8）×revision（真／偽）＝576要求を、別計算と全行で照合した。revision の状態は `not_applicable` 192・`not_requested` 192・`no_provenance` 96・`carried` 80・`no_agent` 16。
- **独立な計算**：訂正された記録のハッシュは、結果の台帳の記録を JSON で正規化して別に計算し、実装の値と照合した（V04・V08・V09・V10・V20）。
- **差分**：P2-q 単独の実行との差分を乱数250要求で確かめた（`coding` を除くと一致、流れは P2-q が報告したことを取り除かない）。
- **乱数**：観察者・出自を乱数で替えた250要求（出力先の宣言の有無、符号の部分集合、revision を含む）を別計算と比べた。
- **変異**：24件を検出（期待の確認22、別計算1、例外1）。
- **検査器の変異**：B21 を追加し、B17〜B20 の目印を更新した。

## 7. 限界と次

- **活動の符号は不透明**です。符号の系の妥当性、符号が示す活動の意味、第三者の符号系の内容は扱いません。
- **`revision` は作成者の読み**です（F37）。`source` など他の役割、`entity.agent`、訂正の理由（自由文）と連鎖の全体の運搬、署名は扱いません。
- **entity の同一性はライブラリの記録の参照とハッシュ**で、FHIR の資源の id や Reference ではありません。出力先の参照への変換は範囲外です。
- **訂正者が不明な訂正は関係を運べません**（F35）。入口で訂正者を求める設計は未実施です。
- **下位の私有の関数（P2-i の記録のハッシュ）に依存**します（F36）。
- 期待・別計算・実装・検査を同じ作成者が書き、読みも共有しているため、読み違いは一緒に入っている可能性があります。独立確認はありません。
- 次の候補は、訂正者を訂正の操作の入口で求めること（F35）、CPC の版の監査、複数の出力先への射影の拡張です。着手前に利用者の確認を取ります。独立確認は将来の英語の別リポジトリで行います。
